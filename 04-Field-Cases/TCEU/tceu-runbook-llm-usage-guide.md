# TCEU 운영 Runbook 사용 안내

기준은 [두 PC 운영 Runbook](./tceu-two-pc-agent-integration-runbook.md) 하나다. Git의 최신판을 읽고, CllC 사본은 버전과 내용을 검증해 갱신한다. 실제 경로·계정·개인 공유 링크는 해당 PC의 제한된 안내에서 확인하며 공개 Git에 넣지 않는다.

**2026-09-19 안내 개정:** 실행 증거는 09-10 인계 기준이다. 선정 KB·결과 공유와 원천 회수 후 CllC·공용 Skill 호출은 통과했다. 현재 재개 대상은 System Master의 자동 시작 지속성 실패이며, 일반 execution lease와 로컬 잔존 자료 전체 부재는 미검증이다. 상태의 정본은 Runbook 7장이다.

CoolFam의 [완료 후 운영 안내](../CoolFam/coolfam-runbook-llm-usage-guide.md)를 차용해 **평소 사용 → 실패 단계 확인 → 필요한 변경만 적용** 순으로 진행한다. TCEU가 CoolFam처럼 전체 완료됐다는 뜻은 아니다. 기존 두 PC 대화와 인계문서를 이어 쓰고, 새 task·새 공유 root·전체 baseline 수집을 기본으로 요구하지 않는다.

평소에는 System Master의 기존 CllC 진입점에서 `Knowledge/`의 manifest와 해당 version의 완성 문서, `Artifacts/`의 task별 manifest·결과를 연다. 최신성은 마지막 성공 갱신 시각과 원천 갱신 시각을 함께 확인한다. 로컬 검색이 필요하면 허용된 출력 폴더에서 실제 검색하고, 바로가기 생성이나 Cloud 열람만으로 Obsidian 검색 성공을 단정하지 않는다.

## 1. 어느 PC에서 무엇을 하는가

| 위치 | 역할 |
|---|---|
| System Master 업무 PC | CnwC 원본 관리·임시 공유/회수, CllC 결과 열람·편집, 사람 검토와 두 PC 결과 통합 |
| TCEU Manager 공용 PC | 실제 AgwA 상태 확인, 허용된 작업 실행, 공유 가능한 KB·결과를 CllC에 저장 |
| Telegram OpenClaw | 현재 권한 안의 구체적인 task 실행·진행·결과 참조. 전체 환경 재구성은 맡기지 않음 |

각 PC는 자기 상태만 직접 확인한다. System Master의 명시적 요청 범위 안에서 문서를 갱신하며 Agent 계정을 사람 승인자로 간주하지 않는다.

## 2. 현재 설치에서 재개

아래 A→B→C를 필요한 순서로 실행한다. 같은 revision·시험 ID를 전달하고 각 PC는 자기 증거만 기록한다. 완료된 공유·설치 항목은 변경 또는 회귀 근거가 있을 때만 다시 점검한다. 이미 승인된 작업 범위는 재승인받지 않고 새 권한·범위가 필요한 부분만 구체적으로 확인한다.

### A. System Master PC — 진단 준비와 최소 수정

```text
작업 TCEU-IMPLEMENT-20260910-01의 자동 시작 실패를 이어서 진단·수정하세요.
최신 TCEU Runbook 6.1~7장과 기존 인계·시험 보고서를 읽고, 이후 수정 증거가 있으면 먼저 반영하세요.
기존 설치를 재사용하고 이미 완료한 공유 연결을 반복하지 마세요.

마지막 재로그온 시험은 watcher 0·0xC000013A·wrapper start 없음으로 실패했습니다.
lifecycle 코드는 별도 self-test를 통과했으나 Operational 로그 활성화는 관리자 권한 부족으로 미적용됐습니다.
이 과거 결과를 현재 상태로 단정하지 말고 실제 task Action·인수·계정·작업 디렉터리·인터프리터·의존성을 대조하세요.
수동 성공 환경과 예약 환경의 차이, 실제 launcher가 수정한 wrapper를 호출하는지 확인하세요.
CoolFam의 runtime 불일치 사례는 조사 항목이며 이번 종료 원인으로 가정하지 마세요.

기존 승인 범위에서 Operational 로그 활성화와 로컬 lifecycle/필요한 launcher 진단을 완성하세요.
권한 부족이면 정확한 실패와 사용자가 실행할 최소 명령을 제공하고 적용 확인 전 재로그온을 요청하지 마세요.
로그 활성 상태와 쓰기를 실제 확인하고 합성 값으로 민감정보 비노출을 검사하세요.
강제 종료 시 종료 행이 남지 않을 수 있으므로 기록 부재만으로 정상 종료를 단정하지 마세요.

변경 전 정의·파일과 복귀 방법을 보존하고 확인된 원인에 필요한 최소 수정만 하세요.
실제 예약 작업 경로로 수동 진단하여 단일 watcher와 로그 기록·비민감 패키징을 확인하세요.
기존 watcher가 있으면 중복 실행하지 마세요. 시험 파일은 원복하고 수동 결과는 별도로 기록하세요.
새 설치·무관한 권한 확대·임의 지연 추가로 문제를 덮지 마세요.

준비와 수동 진단 통과 후에만 사용자가 직접 재로그온하도록 안내하세요. 자동 로그오프·재부팅은 하지 마세요.
기존 인계문서와 시험 보고서의 담당 절에 비민감 결과를 기록하세요.
반환: 실제 변경 / 준비 검증 / 수동 시험 / 원인 또는 미확정 / 복귀 상태 / 다음 PC·복사용 Prompt.
```

### B. System Master PC — 사용자가 재로그온한 뒤

```text
작업 TCEU-IMPLEMENT-20260910-01의 재로그온 자동 실행을 검증하세요.
먼저 준비 단계의 로그 활성화·실행 경로 검증 기록을 확인하세요. 빠졌으면 A의 해당 항목부터 해결하세요.
수동 task 시작 없이 이번 로그인·LogonTrigger 이벤트·wrapper start·PID를 대조하세요.
watcher 정확히 1개와 동일 PID의 최소 10분 지속을 확인하고, 재시작은 별도로 기록하세요.
LastRunTime이나 Running 표시만으로 자동 지속성을 PASS 처리하지 마세요.

위 조건 통과 후 지정 비민감 시험 파일 변경으로 자동 패키징을 확인하고 파일을 원복하세요.
시험 revision/hash와 정상 복귀 revision/hash, 각 생성시각을 기록하세요.
수신 측에 어느 revision이 실제 전달됐는지 확인하지 못하면 양쪽 검증 완료로 표시하지 마세요.
실패 시 종료 근거를 먼저 보존하고, 복구를 수행하면 수동 복구로 따로 기록하세요.

반환: 자동 시작 근거 / 단일 실행 / 10분 지속 / 자동 패키징 / 원복 / blocker.
기존 인계와 보고서에 실제 시각·시간대를 기록하고 TCEU Manager PC용 C 프롬프트에 확인한 값을 넣어 제공하세요.
일반 lease와 잔존 사본 미검증, 기존 KB·회수 시험 PASS를 보존하세요.
```

### C. TCEU Manager PC — 송신 시험 인계 후

```text
동일 작업의 System Master 자동 시험 인계를 읽고 이번 시험에 필요한 수신 확인을 수행하세요.
송신 측이 실제 기록한 revision/hash만 사용하고 값을 추정하지 마세요.
기존 receiver의 상태·수신 패키지·manifest·전체 hash·로딩된 이름/revision을 대조하세요.
시험 revision이 원복 전에 수신됐는지 증거가 없으면 미검증으로 남기고 정상 복귀본 확인과 구분하세요.

일반 실행 중 revision 보호는 아직 미검증입니다. Gateway 정지만으로 모든 실행을 막았다고 가정하지 마세요.
안전한 시험 경계를 확인할 수 없으면 전달·로딩까지만 기록하고 실제 호출·동시 업데이트 시험은 보류하세요.
경계가 확인된 범위에서만 새 비민감 요청으로 해당 Skill을 호출하고 결과와 실제 revision을 대조하세요.
receiver 수동 lock 시험이나 기존 smoke PASS를 일반 lease PASS로 바꾸지 마세요.
실행시간과 배포 지연을 구분하고 최종 원복 revision도 확인하세요.

receiver·Gateway 재설치나 임의 중지를 하지 말고 원천 공유 권한은 건드리지 마세요.
기존 인계·보고서의 담당 절만 갱신하고 양 PC 동시 편집을 피하세요.
반환: 동일 시험의 수신/로딩/호출/원복 판정 / 실제 시각 / 제한사항 / System Master 통합 판정용 복사 Prompt.
일반 lease의 사전조건이 그대로라면 같은 실패 시험을 반복하지 말고 별도 설계 과제로 유지하세요.
```

통합 판정은 System Master가 Runbook 6.2절의 범위별 조건으로 수행한다. 실패한 과거 회차를 삭제하거나, 수동 성공을 자동 성공 회차에 포함하지 않는다. 다른 사례의 7회 관찰이나 선택 항목 제외를 TCEU의 필수 조건·면제로 자동 이식하지 않는다.

### 신규 연결·endpoint 교체 때만: 읽기 전용 baseline

다음 프롬프트는 최초 연결이나 endpoint 교체에만 필요한 부분을 사용한다. 현재 설치에 A~C보다 먼저 반복 적용하지 않는다.

```text
TCEU 두 PC 운영 Runbook의 최신판과 현재 PC의 제한된 경로 안내를 읽으세요.
현재 PC에 적용되는 CnwC·AgwA·CllC 역할과 실제 경로를 구분하고,
경로 존재, 현재 접근권한, 기존 업무 기능과 관련 동기화 상태를 읽기 전용으로 확인하세요.
AgwA는 실행 중인 OpenClaw 설정과 지정 workspace의 일치 여부를 확인하세요.
다른 PC 상태를 추정하지 말고 실제 관찰 / 사용자 설명 / 미검증으로 구분하세요.
없거나 모르는 값은 임의 생성하지 말고 해당 항목과 다음 행동만 알려주세요.
반환: 문서 버전 / PC 역할 / 확인 결과 / blocker / 다음 행동.
민감 원문·비밀·공유 토큰을 읽거나 로그에 남기지 마세요.
```

신규 연결에서는 Runbook 6장의 비민감 시험 범위를 지정한다. 기존 CllC의 원격 소유자·System Master Editor 권한, 같은 결과의 Cloud 반영과 상대 PC 열람·검색, 원천 권한 경계를 확인하고 맞으면 재사용한다. 생성 영역의 편집 의견은 별도 노트에 남긴다. 로컬 폴더 생성이나 바로가기만으로 연결 완료를 판정하지 않는다.

## 3. 일상 작업

다음 짧은 요청에 작업 목적·입력 범위·완료 기준을 자연어로 함께 적는다. 빠진 정보 중 결과에 필요한 것만 질문한다.

```text
TCEU 운영 Runbook에 따라 아래 작업을 수행하세요.
현재 작업에 허용된 자료만 사용하고, 개인 OneDrive 자료는 임시 열람으로 취급하세요.
공유가 없거나 회수되면 필요한 폴더를 Viewer로 재공유해 달라고 요청하세요.
민감 원문과 이를 재현하는 파생물은 AgwA·RAG·로그·CllC에 저장하지 마세요.
보관 여부가 불명확하면 비민감화한 입력 또는 보존 범위 결정을 요청하세요.
보관·공유 가능한 최종 결과는 CllC에 저장하고 기존 사람 편집을 덮어쓰지 마세요.
반환: 결과 상대경로 / 확인 시점 / 로컬 저장·Cloud 반영·상대 PC 확인 상태 / 남은 일.
```

재공유 요청에는 목적, 소유자가 알아볼 비민감 폴더 별칭, 필요한 Viewer 계정과 기간을 해당 비공개 대화에서만 명시한다. 과거 공유 URL·캐시로 회수된 권한을 우회하지 않는다.

Telegram에서도 작업 목적과 허용 입력, 결과 위치, 완료 기준만 전달한다. 다단계 작업은 동일 task ID로 진행하며 외부 발송·원천 변경·권한 확대를 임의 추가하지 않는다.

## 4. 공용 Skill 만들기·수정하기

최초 연결 후 System Master는 CnwC에서 평소처럼 다음과 같이 요청한다.

```text
이 작업을 tceu-shared- 접두어를 쓰는 공용 Skill로 만들어 주세요.
CnwC의 등록된 공용 Skill 위치를 통해 CllC/Shared-Skills 정본에 직접 저장하세요.
기존 Skill이면 같은 정본을 수정하고 별도 사본을 만들지 마세요.
개인 자료·비밀·장치 경로를 제거하고 지원 파일은 상대경로로 참조하세요.
자동 배포 상태에서 해당 revision의 READY가 확인되면 사용 가능한 이름을 알려주세요.
아직 연결되지 않았다면 저장 완료와 AgwA 사용 가능을 구분하고 최초 설정 항목을 알려주세요.
```

목표 운영에서는 저장 뒤 수동 복사·설치·재승인·Git push가 필요 없다. 현재 송신부 지속성 실패가 해결되기 전에는 저장 완료만으로 새 revision 도착을 약속하지 말고 해당 revision의 실제 상태를 확인한다. `READY`는 로딩 준비이며 일반 실행 중 업데이트 보호의 증거가 아니다. 실제 작업 중 같은 Skill의 변경을 겹쳐 시험하지 않으며, 안전한 경계를 강제할 수 없으면 해당 시험을 보류한다. 새 실행 환경이 필요한 경우만 `NEEDS_SETUP` 조치를 진행한다. 공용 Skill 자체를 공개 Git에 게시한다는 뜻은 아니다.

최초 구현은 Runbook 5장의 정본 위치 등록, 저장 감시·자동 패키징, 공용 PC 수신 bridge, OpenClaw extraDirs/watch와 대상 Agent 설정을 한 번 연결하는 작업이다. 패키지 누락·업데이트·퇴역과 다음 요청 반영까지 Runbook 6장 시험을 통과해야 완료다. 현재 송신·수신·실제 호출은 확인됐고, 남은 통합 검증은 Runbook 7장에 따른다. 재설치는 장애가 확인된 범위에서만 수행한다.

## 5. 변경·실패 처리

설정·실행 환경·자동화 범위를 변경할 때는 바꿀 기능, 영향 범위, 현재 버전, 검증 방법, 복귀 방법을 명시한다. 정상 문서 편집과 최초 연결 범위 안의 공용 Skill 저장·자동 반영에는 이 항목을 반복 요구하지 않는다.

접근 실패는 권한 거부·로그인 상태·브라우저 제어 장애를 구분한다. 개인 원본에는 재공유를 요청하고, 공개 운영문서는 최신 Git 파일이나 검증된 열람 사본을 사용한다. 확인할 수 없는 내용을 일반지식이나 기억으로 채우지 않는다.

동기화 충돌·민감정보 저장·권한 밖 접근·업무 장애가 생기면 관련 작업을 멈추고 Runbook 6장에 따라 복귀한다. 단순 queue·index 변화는 정상 운영의 변화인지 먼저 확인한다.

문제 확인은 **원천 변경 → 송신 패키징 → Cloud 전달 → 수신 검증 → 로딩 → 실제 호출** 중 실패한 단계부터 시작한다. 마지막 정상본과 새 후보를 구분하고 필요한 전후 단계만 확인한다. 누락된 dependency·로그 권한·runtime 경로를 해결하기 전 같은 자동 시험을 반복하지 않는다. 합성 표본이 특정 분기를 실행하지 않았다면 `NOT_EXERCISED`로 남긴다.

## 6. 문서 갱신

```text
이번에 확인한 비민감 사실만 TCEU Runbook의 현재 상태에 반영하세요.
Git 최신 버전과 내 편집 기준을 비교하고 다른 변경을 보존하세요.
사용자 설명 / 직접 관찰 / 미검증을 구분하고, 과거 HOLD를 근거 없이 완료로 바꾸지 마세요.
운영 기준과 실행 안내가 중복되면 한 곳에만 유지하고 링크하세요.
문서 버전·검토일, 내부 링크, 개인정보·토큰·기기 경로 제외를 확인하세요.
요청된 Git 업데이트가 성공한 뒤 같은 내용을 CllC 열람 사본으로 갱신하고
내용 또는 SHA-256 일치를 확인하세요. 로컬 반영과 Cloud 동기화는 따로 보고하세요.
```

Git 갱신 완료는 원격 commit과 대상 파일을 다시 읽어 확인한다. CllC에는 정본 URL·문서 버전·검증 commit을 표시한다. 편집·게시가 실패하면 변경안과 남은 일을 반환하며 성공으로 보고하지 않는다.
